# ProcessGuardian 0.1.22 架构巡检

范围：设置页、共享配置与进程枚举、root 守护进程、SpringBoard 前台探针、CPU 监控、StayAlive 重拉与断言、RootHide 路径、安装卸载脚本及构建工作流。

## 已处理

| 问题 | 处理 |
| --- | --- |
| 更换目标时仍保留旧应用名称备注 | 目标改变时用新应用名称或进程标识替换备注；重选同一目标保留备注 |
| 每个配置各扫一遍进程表，状态发布又重复查找 | 一轮配置处理和状态发布共用批量 PID 快照；一个 PID 只取一次路径；同一 app 的 Info.plist 在该快照中只读一次 |
| 一轮反复读配置 | 读取一次后传入解析、执行、状态发布；日志大小设置随此快照更新 |
| 设置主页每行扫描和读取状态文件 | 整页共用一次进程快照、一次状态文件读取；候选页在加载时批量取运行状态 |
| 全局关闭时每次事件仍重复枚举和记日志 | 配置未变且无待撤销记录时跳过进程扫描；30 分钟巡检仍更新状态 |
| 密集事件反复推迟执行 | 第一次事件后合并 600ms 内请求，避免持续事件使巡检无限后移 |
| 前台/启动事件被当作配置改变 | 独立 ProcessChanged 通知只通知守护进程；CPU 监控和 StayAlive 不再因此重复重载配置 |
| CPU 每次采样重复查询用量和读取 Info.plist | 复用一次用量查询，同时检查 PID 启动时间及路径；真正结束进程前仍复核包名 |
| 初始化扫描可能与工作队列并发 | 初始化扫描也在同一串行队列执行；每轮有独立 autoreleasepool |
| 恢复默认时已有设置残留 | 恢复已有接管设置后再解除跟踪；部分选项关闭时先撤销旧设置再应用新配置 |
| 删除配置时可能向旧 PID 对应的其他名称进程写入 | 撤销前要求 PID 仍在本轮该标识的匹配结果中 |
| 注销后恢复队列只处理首项 | 消费回调开始时清除“已排队”标志，使下一项能正常排队 |
| 旧 StayAlive 写入器使用已废弃 apps/global 字段 | 删除无调用方的写入 API、导航持久化和相关声明；保留实际读配置与运行时状态路径 |
| 配置导入类型错误可导致设置崩溃；导出回调误入导入处理 | 验证根节点、条目与字段类型；导出不使用导入代理；导入与恢复后立即刷新列表 |

## 性能证据与验证边界

`tests/runtime.m` 在 macOS 上编译真实 MCCommon 和守护扫描代码，用模拟进程表验证批量/逐项查询等价、扩展包匹配、进程消失后的新快照、重复巡检不重复写入、恢复默认和关闭后的空闲路径。计数验证五个目标从五次独立枚举减少为一次批量枚举。此计数不是设备 CPU 百分比测试。

原有 Jetsam 返回值、iOS 15/16 档位检查继续执行。CI 仍验证 RootHide 包目录、arm64e 架构和守护程序签名权限。Windows 环境不能运行 iOS 设置界面或 SpringBoard 私有 API；真实 CPU 用量、长时间保活和多应用注销恢复需设备验证。

## 保留的边界与后续风险

- 一个配置仍按首个匹配 PID 应用限制。主 app 与扩展共享包名时，不能保证它们全部采用同一设置；本次维持现有目标选择规则。
- 同一名称的 PID 被回收后复用，单靠名字和 PID 无法完全区分进程世代。CPU 杀进程已有启动时间和路径复核；守护限制恢复只新增了名称/包名匹配检查。
- Nice=0、Jetsam=-1 是本项目的“不主动设置”约定。Jetsam 写入 0 实际是空闲档位，旧界面所称“系统接管”并不等于恢复修改前的原始值。准确还原原值需要保存修改前状态并验证运行中被系统调整的情况，不能宣称本版本已经做到。
- 内存限制的 -1 值由内核解释，旧界面“不受限制”的说明不应视作无限内存保证。内核策略、RunningBoard 断言与优先级覆盖仍需真机观察日志。
- StayAlive 的私有断言和启动接口、上滑关闭识别、崩溃退避需要真机回归；本次未更换其断言架构。定时/网络/电量策略代码保留，避免扩大行为变化。
- 手工通过 Filza 写入无效类型绕过导入校验，仍可能影响消费者；本次导入入口拒绝错误容器类型，不声称所有外部编辑都已校验。
- 卸载脚本仅卸载本项目 launchd 服务、终止本项目守护进程，没有删除或修改 ElleKit 文件；已注入 SpringBoard 的代码需正常注销后卸载出内存。

这次采用每轮短生命周期快照，而非长期 PID 缓存；维持事件响应和 1800 秒兜底巡检。未引入新依赖或新的后台常驻组件。
